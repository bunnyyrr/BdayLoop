# BdayLoop

Бэкенд для «BdayHub» — сервиса, который помогает не забывать про дни рождения друзей, дарить подарки вскладчину и обсуждать их в закрытом чате. Изначально хакатонный проект на Firebase, переписывается с нуля как pet-проект для практики Java backend-разработки (портфолио для стажировки в Т-Банк).

Проект идёт поэтапно — от голой Java до полноценного Spring Boot, чтобы на каждом шаге руками пощупать, что именно фреймворк потом сделает за тебя. Этот README описывает **первый этап**.

## Этап 1 — чистая Java

Никакого Spring, никакой ORM. Всё, что обычно берёт на себя фреймворк — HTTP-роутинг, сериализация, DI, сессии — написано руками, чтобы понимать, что происходит под капотом.

### Стек

- **Java 26**, Maven
- **Embedded Jetty + Servlets** — HTTP-слой, без Spring MVC
- **Raw JDBC** — без ORM, весь SQL написан вручную
- **PostgreSQL 16** — в Docker
- **Jackson** — (де)сериализация JSON
- **BCrypt** — хэширование паролей
- **HttpSession** — аутентификация по cookie-сессии
- **JUnit 5 + Testcontainers** — тесты DAO-слоя на реальном Postgres в контейнере
- **GitHub Actions** — CI на каждый push и pull request
- Фронтенд — vanilla HTML/JS/fetch, без сборки, только для ручной проверки API

### Архитектура

Строго слоями, без исключений:

```
Servlet → Service → DAO → PostgreSQL
```

- **DAO** — «глупый», только SQL и проверки целостности (0 затронутых строк → not found). Никакой бизнес-логики.
- **Service** — вся бизнес-логика и проверки прав («можно ли этому пользователю это делать»).
- **Servlet** — только перевод HTTP ↔ JSON, маршрутизация и коды ответов.

DAO спрятаны за интерфейсами (`UserDao`, `GroupDao`, `GiftDao`, `MessageDao`) — Service зависит от абстракции, а не от конкретной реализации (DIP), конкретные `*Impl`-классы собираются вручную в `Application.java`, композиционном корне приложения.

### Доменная модель

`users`, `groups`, `group_members`, `group_subscriptions`, `subscriptions`, `gifts`, `messages` — полная схема в [`db/schema.sql`](db/schema.sql), применяется автоматически при первом поднятии контейнера.

### Функциональность

- Регистрация, вход/выход, роль `USER`/`ADMIN`
- Поиск пользователей — по имени, username или id
- Просмотр и редактирование профиля
- Группы: создание, вступление/выход, подписка, переименование, удаление
- Подарки: добавление, удаление, список по пользователю
- Чат про подарок — сообщения между подписчиком и именинником, доступ только после подписки
- Массовый импорт пользователей администратором

### Запуск

**1. База данных**

```bash
cp .env.example .env   # заполнить POSTGRES_DB / POSTGRES_USER / POSTGRES_PASSWORD
docker compose up -d
```

**2. Бэкенд**

Задать те же три переменные окружения в Run Configuration и запустить `Application.main()`. Сервер поднимается на `http://localhost:8080`.

**3. Фронтенд**

```bash
cd frontend
python3 -m http.server 8123
```

Открыть `http://localhost:8123/html/login.html`.

### Тесты и CI

```bash
mvn test
```

Тесты DAO-слоя поднимают отдельный Postgres в Docker через Testcontainers на время прогона — реальная база, не моки. GitHub Actions гоняет тот же `mvn test` на каждый push и pull request.

### Осознанно отложено на этап 2 (Spring + Hibernate)

- Напоминания о днях рождения
- Смена пароля — сейчас можно поменять только имя, дату рождения и username
- Проверка владельца при переименовании группы
- Атомарность массового импорта — при ошибке в середине списка уже созданные пользователи остаются в базе
